# S7 (ibe.s7.ru) — почему источник выключен

Статус: `s7_direct` отключён (`s7_enabled: false` в `config.yaml`/`config.example.yaml`).
Код (`src/aviapars/adapters/s7_direct.py`, `src/aviapars/solver/browser_solver.py`,
команда `/s7_session` в `admin.py`) не удалён — оставлен на случай
возврата. Короткая версия для конфига и ARCHITECTURE.md; здесь — подробный разбор
того, с чем столкнулись, и как устроена защита у S7.

## С какими проблемами столкнулись, по порядку

**1. Challenge-заглушка вместо страницы поиска.** Первый запрос к `ibe.s7.ru/air`
без пройденной проверки отдаёт не результаты, а HTML с обфусцированным
JS-загрузчиком (`js-challenge-loader`) вместо `execution`/`ibe_conversation` —
идентификаторов Spring Webflow-сессии, без которых не собрать следующий запрос.

**2. Обфусцированный challenge-скрипт.** Сам скрипт (`checkjs`, ~347КБ) реально
трогает `canvas.getContext`, `navigator.webdriver` и другие браузерные API — то
есть требует настоящего DOM/JS-окружения, голый JS-движок без браузера его не
пройдёт в принципе.

**3. Автоматизированный браузер тоже не проходит.** Пробовали `patchright`
(anti-detect форк Playwright, уже используется как fallback в `browser_solver.py`)
headless-режимом на трёх разных сетях (домашний IP, VPN, сама VDS) — во всех трёх
случаях мгновенный `403 Forbidden`, экран challenge даже не показывается. То есть
блокируется не по IP/сети, а по самому факту, что браузер управляется CDP
(Chrome DevTools Protocol) — независимо от анти-детект патчей.

**4. Обычный браузер человека — проходит.** Подтверждено живым HAR: реальный,
не автоматизированный Chrome челлендж проходит стабильно и получает рабочую сессию
с ценами.

**5. Кука с долгим сроком жизни, но реплей через другой HTTP-клиент — не работает.**
Ключевая антибот-кука (`cfidsw-s7-ibe`) в живом захвате имела срок жизни около года.
Казалось бы: один раз пройти challenge браузером, дальше просто слать сохранённые
куки через быстрый `curl_cffi` (имитация TLS-отпечатка Chrome, без реального
браузера) — дёшево и быстро. Проверили дважды:
- Сначала теоретически, по HAR: **каждый** `POST /air` с
  `_eventId=getExtendedSearchResult` несёт два заголовка —
  `x-gib-fgsscw-s7-ibe` и `x-gib-gsscw-s7-ibe` — и их значения **разные на каждый
  из 11 запросов** одной и той же сессии, не разные один раз при заходе.
- Потом живьём: админ вручную сходил на `ibe.s7.ru`, экспортировал 18 свежих кук
  (Cookie-Editor), они были сохранены и реплеены через `curl_cffi` — результат
  `BLOCKED`. Кука настоящего человека, только что прошедшего challenge, не
  спасает реплей через другой клиент. Значит дело не в протухшей/неполной сессии
  — нужны именно per-request заголовки, которые кука сама по себе не даёт.

## Как устроена защита (в общих чертах — не рецепт обхода, а как работает класс таких систем)

Это продукт Group-IB (сокращение `gib` в именах заголовков), в конкретной
реализации известный как ServicePipe. По механике — тот же класс, что
PerimeterX/HUMAN, DataDome, Akamai Bot Manager, Cloudflare Bot Management,
Variti, Qrator (тот же класс защиты стоит и у `rossiya-airlines.ru`/группы
Аэрофлот, и у некоторых других источников в этом проекте — см. ARCHITECTURE.md).
Устройство обычно послойное:

**Слой 1 — классификация первого запроса.** Сервер смотрит на входящий запрос
(нет нужных кук, подозрительный TLS/HTTP-отпечаток, нетипичные заголовки) и
вместо реальной страницы отдаёт challenge-страницу вместо контента.

**Слой 2 — фингерпринтинг среды исполнения.** JS на challenge-странице собирает
десятки сигналов: canvas- и WebGL-отпечаток (рендер конкретной видеокарты/драйвера
через `canvas.getContext`/`WebGLRenderingContext`), audio-context отпечаток,
список шрифтов, разрешение и глубину цвета экрана, часовой пояс, языки браузера,
свойства объекта `navigator` (включая `navigator.webdriver`, который автоматизация
по умолчанию выставляет в `true`), поведение `Function.prototype.toString` —
у функций, пропатченных CDP/автоматизацией, оно отличается от нативного
V8-байткода. Таймингом отдельных вызовов иногда меряют ещё и «слишком идеальную»
скорость выполнения, характерную для скрипта, а не человека.

**Слой 3 — детект автоматизации на уровне протокола.** Отдельно от
фингерпринтинга среды — детект самого факта, что браузером управляют через CDP:
специфичные для автоматизации свойства окна/рантайма, разница в поведении
некоторых API при включённом Runtime-домене CDP, иногда — задержки/паттерны
сетевых вызовов, характерные для управляемой сессии. Именно на этом палится
patchright несмотря на анти-детект патчи — вендор регулярно обновляет список
проверяемых сигналов, и «undetected»-форки всегда догоняют, а не опережают.

**Слой 4 — выдача trust-куки.** Пройдя слои 2-3, сервер выдаёт долгоживущую куку
(`cfidsw-s7-ibe` в данном случае) — она говорит «эта сессия один раз прошла
фингерпринтинг», но сама по себе не открывает доступ к данным напрямую.

**Слой 5 — подпись каждого последующего запроса.** На каждой странице (не только
challenge) подгружен SDK антибота, который перехватывает нативные `fetch`/
`XMLHttpRequest`. На каждый исходящий запрос к защищённым эндпоинтам он
довешивает подписанные заголовки (в случае S7 — `x-gib-fgsscw-s7-ibe`,
`x-gib-gsscw-s7-ibe`), значение которых пересчитывается заново на каждый вызов
из комбинации: значения trust-куки, URL/тела запроса, серверного nonce/таймстампа
и заново снятого отпечатка среды. Это по сути HMAC-подобная подпись с ключом/
алгоритмом, зашитым (и обфусцированным) в JS-бандле, которая проверяется на
сервере. Именно поэтому простой реплей куки через другой HTTP-клиент не работает
— клиент, который не выполняет этот JS, не может выпустить валидную подпись
для нового запроса, даже имея легитимную куку.

**Слой 6 — защита от статического анализа.** Скрипт, который считает подпись,
обычно сильно минифицирован/обфусцирован, иногда с частью логики в WASM
специально для затруднения реверса, плюс детект открытых devtools (при
обнаружении — либо блок, либо отдача заведомо неверной телеметрии, чтобы
испортить данные того, кто пытается разобраться).

**Слой 7 — сетевой уровень, отдельно от JS.** Многие такие системы дополнительно
сверяют TLS ClientHello отпечаток (JA3/JA4) и порядок HTTP/2-фреймов с заявленным
User-Agent. `curl_cffi` неплохо имитирует байты TLS-рукопожатия Chrome, но не
саму JS-среду и не порядок фреймов идеально — ещё один независимый вектор детекта
поверх подписи заголовков.

## Как это обычно обходят (в индустрии — общая картина, не рецепт для S7)

Для общего понимания, чем в принципе занимаются, когда всё же решают идти этим
путём — без привязки к тому, что здесь применимо или планируется. Примерно по
возрастанию сложности:

1. **Прокси-пулы (дата-центр/резидентские/мобильные).** Решают только слой 1
   (IP-репутация/ASN) — сами по себе не проходят фингерпринтинг, детект CDP или
   подпись запросов. Резидентские/мобильные пулы (реальные IP обычных
   пользователей, обычно через SDK, встроенный в сторонние приложения за
   вознаграждение) дороже дата-центровых именно потому, что реже банятся по
   классу адреса — но это работает только против сетевого слоя.
2. **Anti-detect браузеры / фермы профилей.** Коммерческие инструменты
   (Multilogin, GoLogin, AdsPower и аналоги) держат пул отдельных браузерных
   профилей с разными, но правдоподобными отпечатками (canvas/WebGL-шум,
   шрифты, часовой пояс), обычно без headless (через виртуальный дисплей) —
   изначально продукт для фарма рекламных/торговых аккаунтов, тем же
   инструментарием закрывают и слои 2-3.
3. **Сервисы решения капчи/челленджей.** Клик-фермы или ML-решатели (2captcha,
   Anti-Captcha, CapMonster и т.п.) — решают визуальные капчи, к JS-подписи
   вроде здешней впрямую не относятся, иногда используются в связке с
   остальным.
4. **Коммерческие "unlocker" API.** ScraperAPI, Bright Data Web Unlocker,
   Zyte Smart Proxy Manager, Oxylabs и похожие — продают уже собранную связку
   «прокси-пул + браузерная ферма + реверс-инженерия конкретных
   антибот-вендоров», оплата за успешный запрос. По сути отдельная индустрия,
   которая непрерывно ведёт гонку вооружений именно с такими вендорами
   (Group-IB, DataDome, PerimeterX/HUMAN, Akamai) и переделывает свою часть
   при каждом их обновлении — это full-time работа команды, не разовый фикс.
5. **Прямой реверс алгоритма подписи.** Деобфускация challenge-скрипта и
   воспроизведение самой сигнатуры без браузера (либо в урезанном JS-движке,
   либо переписав алгоритм на своём языке после статического анализа).
   Ломается при любом обновлении обфусцированного скрипта на стороне вендора —
   у серьёзных антибот-продуктов это происходит регулярно, так что рецепт
   живёт до следующего обновления, а не постоянно.
6. **Маркетплейсы готовых сессий/кук.** Покупка уже решённых сессий у тех, кто
   их насобирал — не помогает конкретно здесь: проблема S7 не в получении
   сессии (её и вручную получить не проблема), а в per-request подписи,
   которую готовая кука не даёт.
7. **Легитимный путь — то, чем на практике пользуются настоящие агрегаторы.**
   Google Flights, Skyscanner и подобные получают тарифы через официальные
   GDS-фиды, партнёрские API и коммерческие договоры с перевозчиками — не
   пробивая чью-то защиту. В этом проекте эквивалент — `travelpayouts.py`
   (см. раздел выше).

## Почему не стали обходить

Собранные факты (headless-браузер блокируется на слое 3, кука настоящего
человека не спасает реплей на слое 5, нужны per-request подписи) — это не
препятствие на пути к рабочему адаптеру, а уже готовый ответ: S7 намеренно
и инженерно отличает автоматический трафик от браузерного и подписывает
каждый запрос. Дальнейшие шаги в эту сторону (гонять патченный браузер без
headless специально чтобы выглядеть убедительнее для детектора, либо
выполнять запрос из живого JS-рантайма страницы, чтобы SDK антибота сам
подписал заголовки) — это обход защитного механизма, который сайт
целенаправленно построил, а не парсинг публичной страницы. Личное
использование и небольшая нагрузка (один пользователь, интервал между
запросами 15с) не меняют категорию действия — метод остаётся обходом
средства защиты, а не сбором данных с открытой страницы.
