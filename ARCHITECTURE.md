# Архитектура

Полное обоснование решений и историю ревизий — см. [plans/squishy-scribbling-dawn.md](plans/squishy-scribbling-dawn.md).
Этот файл — сжатый снимок текущей структуры, обновляется вместе с кодом.

## Что делает проект

Telegram-бот, работающий на одном процессе (VDS 1 vCPU / 1GB RAM / 15GB disk, Ubuntu 24.04):
опрашивает источники цен на авиабилеты по маршрутам, заданным пользователем через бота
(`/add`), и уведомляет, когда цена падает ниже заданного порога. Живой ходовой скелет уже
работает end-to-end (route → travelpayouts → validator → dealer → notifier → Telegram),
проверено смоук-тестом с реальным токеном бота. Есть и разовый интерактивный поиск (`/search`),
переиспользующий тот же `combiner`. Жд/автобусные источники и подтверждающие адаптеры
авиакомпаний, смешанные маршруты через хаб — ещё не построены (Phase B-E, см. план); ниже
описано только то, что реально существует в коде сейчас.

## Структура каталогов

```
src/aviapars/
├── config.py                    # pydantic-settings: секреты из .env, тюнинги из config.yaml
├── db/                          # engine, миграции, репозитории, типизированные модели
├── telegram/
│   ├── bot.py                   # Bot/Dispatcher, регистрация роутеров
│   ├── handlers/                # start, add, search (оба FSM-мастера), routes, status, admin
│   ├── place_picker.py          # общий виджет выбора места — переиспользуют add и search
│   ├── keyboards.py, states.py, format.py
├── scheduler/
│   ├── tick.py                  # цикл раз в 60с: due-маршруты + отложенные notify-задачи
│   └── worker.py                # обработка одного маршрута
├── adapters/
│   ├── base.py                  # протокол SourceAdapter, Offer/Leg/SearchQuery
│   ├── registry.py               # rate-limit + circuit-breaker + кэш + таймауты — единая обёртка
│   ├── ratelimit.py, circuit.py, cache.py
│   └── travelpayouts.py          # единственный подключённый источник на сегодня
├── domain/                       # combiner (точка входа поиска, пока только прямые рейсы),
│                                    validator (freshness gate), dealer (проверка порога), places.py
└── notify/                       # notifier.py (форматирование/дедуп/тихие часы), dedupe.py

data/
├── migrations/                     # 001 — вся схема; 002 — уникальный индекс (kind, iata) для сида
└── seed_places.py                  # тянет реальный дамп городов/аэропортов Travelpayouts (578 строк RU),
│                                      идемпотентно; жд-станции появятся с адаптером Яндекс.Расписаний
deploy/                             # systemd unit, deploy.sh, INSTALL.md
tests/fixtures/                     # записанные реальные ответы источников
```

`health/` в дереве пока пустой — circuit-breaker живёт в `adapters/circuit.py` и персистится
через `db/repo_health.py`, отдельный модуль не понадобился.

## Поток данных (то, что реально есть)

```
/add → routes (БД) → scheduler.tick (раз в 60с) → worker.process_route
                                                        → combiner.search_itineraries()
                                                        → validator.freshness_gate
                                                        → dealer.crosses_threshold
                                                        → notifier.send_deal → Telegram
```

`scheduler/tick.py` обрабатывает due-маршруты последовательно в цикле, а не через отдельный
пул воркеров с очередью `jobs` — с одним зарегистрированным адаптером это лишняя сложность.
Таблица `jobs` пока используется только для одного случая: отложенная доставка уведомления,
если у пользователя тихие часы (`kind='notify'`). Полная схема планировщика с пулом воркеров —
на будущее, когда число источников/маршрутов сделает последовательную обработку медленной.

`combiner.search_itineraries()` — общая точка входа для "как добраться из A в B". И
`scheduler.worker`, и `telegram/handlers/search.py` (`/search`) вызывают её же, различаясь
только `SearchOpts`; логика фильтрации адаптеров и freshness gate не дублируется. Пока строит
только прямые рейсы (без пересадок/хабов — это Phase D). Кнопка «Отслеживать» под результатами
`/search` не сохраняет отдельную сессию (`search_sessions` из плана — Phase E), а просто
переносит уже известные origin/dest/mode/дату в FSM-состояние мастера `/add`, пропуская
повторный ввод.

## Адаптеры источников

Каждый источник цен — класс, реализующий протокол `SourceAdapter` (`adapters/base.py`):
`search()` никогда не бросает исключение, вся политика retry/backoff/circuit-breaker/кэша
живёт в общей обёртке реестра (`adapters/registry.py`), а не в самом адаптере. Добавление
нового источника — один новый файл + одна строка регистрации.

Два тира: `discovery` (дёшево, пакетно, может быть устаревшим) и `confirmation` (узкий live-запрос
к конкретному сайту перевозчика). Сейчас подключён только `travelpayouts` (discovery). Прямые
адаптеры авиакомпаний (Rossiya, S7 и т.д.) не построены — для них нужно вручную найти реальный
JSON/XHR-эндпоинт через devtools в браузере, чего инструментами агента сделать нельзя; отложено
намеренно, не забыто.

**Важная находка при подключении Travelpayouts (проверено на живом API):** эндпоинт
`v2/prices/month-matrix` не даёт ни авиакомпанию, ни номер рейса, ни точное время — только
дату, цену, число пересадок и суммарную длительность. Поэтому `Leg.carrier`/`number`/`arrive_utc`/`tz`
опциональны (`time_precision` показывает честно, когда время — просто дата), а адаптер
отбрасывает рейсы с пересадками (`number_of_changes > 0`) — достраивать их из этих данных
означало бы выдумывать хаб и перевозчика.

## Ключевые решения и почему

- **SQLite вместо сервера БД** — нулевой холостой RAM на боксе с 1GB.
- **Без headless-браузера никогда** — Playwright/Selenium съедают 300-500MB на инстанс. Если
  сайт защищён по TLS-отпечатку — обход через `curl_cffi`, не браузер.
- **Python, не Go/Node** — узкое место не CPU (I/O-bound, вежливые паузы к источникам), а скорость
  добавления нового адаптера; для реверс-инжиниринга сайтов у Python богаче экосистема и примеры.
- **Секреты vs тюнинги разделены** — `.env` только для токенов/ключей, `config.yaml` для лимитов
  (кол-во воркеров, HTTP-конкурентность, TTL кэша и т.д.) — поднять лимиты на новом VDS = поменять
  конфиг, не код.
- **Аварийная остановка только для владельца** — `/stop` проверяет `ADMIN_TG_ID`; systemd юнит на
  `Restart=on-failure`, чтобы чистая остановка не перезапускалась сама. cgroup-лимиты (`MemoryMax`)
  гарантируют, что бот не заберёт ресурсы у Tailscale/SSH на той же VDS вне зависимости от команд.
- **Заложена, но не построена generalization под ЖД-конкурентов/автобусы/другие страны** —
  `Mode` enum, поле `countries` у адаптера, таблица пересадок с fallback по стране — см. план §1/§5/§8.

## Тесты

11 тестов (`mypy --strict` + `pytest`, оба чистые):
- `tests/adapters/test_travelpayouts.py` — адаптер на записанном реальном ответе
  (`tests/fixtures/travelpayouts/`); при поломке сайта источника цикл починки: записать новый
  fixture → поправить парсер → тесты зелёные, без тыканья в прод.
- `tests/test_walking_skeleton.py` — интеграционный тест всей цепочки на временной SQLite:
  маршрут ниже порога триггерит уведомление, маршрут выше порога — нет.
- `tests/test_notifier.py` — тихие часы (переход через полночь), дедуп/дневной лимit уведомлений.

Реальный баг, пойманный интеграционным тестом: `notifications_sent.sent_at` и `users.created_at`
писались через `datetime('now')` SQLite (другой формат строки, без смещения), а читались через
`datetime.fromisoformat()` — молча ломало и cooldown, и дневной лимит. Оба места переписаны на
явный `datetime.now(timezone.utc).isoformat()`, как везде в проекте.

`data/seed_places.py` тестами не покрыт (дёргает живой сетевой дамп Travelpayouts) — проверен
вручную: загрузка, идемпотентность повторного запуска, корректная привязка аэропортов к городу
и определение Москвы как хаба по числу аэропортов.
