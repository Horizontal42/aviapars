# Архитектура

Этот файл — сжатый снимок текущей структуры и решений, обновляется вместе с кодом.

## Что делает проект

Telegram-бот, работающий на одном процессе (VDS 1 vCPU / 1GB RAM / 15GB disk, Ubuntu 24.04):
опрашивает источники цен по маршрутам, заданным пользователем через бота (`/add`), и уведомляет,
когда цена падает ниже заданного порога. Живой ходовой скелет работает end-to-end (route →
combiner → validator → dealer → notifier → Telegram), включая **маршруты через хаб** (например,
Екатеринбург→Москва→Сочи) — комбинатор ищет оба плеча отдельно и сравнивает с прямым рейсом по
итоговой цене. Проверено вживую на реальных API. Подтверждающие адаптеры авиакомпаний есть для
S7 и для Аэрофлота/России (общий инвентарь группы); Pobeda/Ural/Utair — ещё нет. Реальные цены
на поезда есть, но через неофициальный `rzd_direct`, не через Яндекс.Расписания (см. "Адаптеры
источников" ниже); ниже описано только то, что реально существует в коде сейчас.

## Поток данных (то, что реально есть)

```
/add → routes (БД) → scheduler.tick (раз в 60с) → worker.process_route
                                                        → dates.resolve_date_plan() (+курсор)
                                                        → combiner.search_itineraries()
                                                        → validator.freshness_gate
                                                        → dealer.crosses_threshold
                                                        → notifier.send_deal
                                                             instant: шлёт сразу
                                                             тихие часы / digest: рендерит карточку,
                                                             кладёт в jobs (kind='notify'), тик
                                                             доставляет её при наступлении run_after
```

`scheduler/tick.py` обрабатывает due-маршруты последовательно в цикле, а не через отдельный
пул воркеров с очередью `jobs` — с одним зарегистрированным адаптером это лишняя сложность.
Таблица `jobs` используется для отложенной доставки уведомлений: и тихие часы, и digest-режим
(см. ниже) — оба случая «отправь не сейчас, а позже» решаются одним и тем же механизмом.
Полная схема планировщика с пулом воркеров — на будущее, когда число источников/маршрутов
сделает последовательную обработку медленной.

## Порог цены: один на маршрут или отдельный по видам транспорта

`routes.max_price` — один потолок на весь маршрут — остаётся дефолтом и ничего не меняет для
существующих маршрутов. Маршрут, следящий больше чем за одним видом транспорта (`mode_pref = auto`),
может вместо этого задать **отдельный потолок на каждый вид**: «самолёт дешевле 8000 ₽ ИЛИ поезд
дешевле 4000 ₽». Это опция, а не новый обязательный шаг.

- **Хранение — `routes.max_price_by_mode` (миграция 008), JSON, nullable.** `NULL` = один общий
  потолок в `max_price`, ровно как было; заполнено = `{"plane": 800000, "train": 400000}` в
  минорных единицах, с той же валютой `max_price_currency`. Форма повторяет прецедент, заданный
  `mode_pref` (§4): значение, ключуемое строкой режима, так что третий режим (автобус, §5)
  добавит ключ, а не колонку. Изменение чисто аддитивное — одномодовые маршруты не затронуты
  вовсе, а `max_price` сохраняет прежний смысл.
- **`max_price` остаётся NOT NULL и осмысленным даже при заполненных пер-модовых потолках**: он
  хранит больший из них и служит потолком для **смешанного** составного маршрута (плечо самолётом
  плюс плечо поездом). Такая цена — не «цена на самолёт» и не «цена на поезд», её не описывает ни
  один из двух потолков, а складывать два потолка, каждый из которых выбирался под целую поездку,
  значило бы сравнивать одну комбинированную цену с числом, которого никто не называл. Больший из
  двух — это максимум, который человек назвал за эту поездку хоть каким-то одним способом, то есть
  честная граница для поездки, которая частично и то, и другое. Same-mode через хаб
  (самолёт→хаб→самолёт) смешанным не считается и берёт потолок своего режима.
- **`dealer.threshold_for(route, modes)` — единственное место, где это решается.**
  `crosses_threshold()` теперь принимает режимы маршрута-кандидата и спрашивает у неё потолок;
  без аргумента поведение прежнее (общий потолок). `notifier` рисует в карточке именно тот
  потолок, по которому вариант реально прошёл, а не голый `max_price`.
- **Два следствия в `scheduler/worker._deals_to_send()`.** Во-первых, самый дешёвый вариант больше
  не обязательно проходящий: дешёвый поезд выше своего потолка может стоять перед самолётом ниже
  своего, поэтому сканируется весь (отсортированный по цене) список, а не только его голова — при
  общем потолке это в точности прежнее поведение. Во-вторых, «самолёт дешевле 8000 ИЛИ поезд
  дешевле 4000» — два независимых запроса, и отправка только более дешёвого молча отвечала бы на
  половину; поэтому при заполненных пер-модовых потолках уведомление уходит по одному на каждую
  группу транспорта (группировка по набору режимов — та же разбивка, что на экране результатов
  `/search`). Маршрут на общем потолке по-прежнему шлёт ровно одно сообщение за цикл.
- **Мастер спрашивает лишний шаг только когда есть что делить.** `/add` при `mode_pref = auto`
  вставляет `AddRoute.threshold_scope` («Один порог на всё» / «Отдельно по видам») перед вводом
  суммы; при «отдельно» — два ввода подряд, самолёт затем поезд, в порядке `MODE_LABEL`. Маршрут
  «только самолёт» или «только поезд» этого шага не видит вообще и проходит тот же мастер, что и
  раньше. Мост «💾 Отслеживать» из `/search` ведёт сразу к одному общему порогу: он предзаполняет
  сумму из конкретного найденного варианта, и `mode_pref` там берётся из режимов самого варианта —
  «auto» получается только для смешанного хаб-маршрута, к которому пер-модовые потолки всё равно
  не применяются.
- **Карточки показывают то, что реально действует.** `format.describe_thresholds()` рисует
  «8 000 ₽» для общего потолка и «✈️ 8 000 ₽ · 🚂 4 000 ₽» для раздельных — и в подтверждении
  `/add`, и в карточке маршрута `/routes`.

## Когда уведомлять: instant против digest

`routes.notification_mode` — выбор пользователя на каждый маршрут: `instant` (по умолчанию,
сообщение сразу, как цена перешла порог) или `digest` (каждое пробитие порога — всё равно
отдельное уведомление, просто доставка каждого из них откладывается до одного и того же
времени дня, а не рассыпается по дню поштучно).

- **Первая версия была не тем, что просил пользователь, и её откатили.** Миграция 006 заводила
  таблицу `route_digests`, которая держала только *самую дешёвую* находку суток, затирая более
  ранние — то есть два разных пробития порога за день схлопывались в одно сообщение. Пользователь
  явно поправил: каждое пробитие порога должно остаться отдельным уведомлением, просто с общим
  временем доставки. Миграция 007 дропает `route_digests`; аккумулятор больше не нужен.
- **Digest переиспользует механизм отложенной доставки тихих часов, а не изобретает новый.**
  `notifier.send_deal()` и раньше умел «отрендерить карточку сейчас, положить в `jobs` с
  `run_after`, доставить позже» — именно это нужно и digest-режиму. Условие деферра теперь
  `is_quiet_hours(user, now) or route.notification_mode == "digest"`; при срабатывании обеих
  причин ничего не меняется — используется тот же `next_quiet_hours_end`.
- **Ветвление — в доставке, не в домене.** `dealer.crosses_threshold()` остаётся mode-agnostic:
  «достаточно ли дёшево» — факт о цене, а не о том, как человек хочет об этом услышать. Вся
  развилка живёт внутри `notifier.send_deal()`.
- **Якорь времени — `quiet_hours_end`, не полночь.** Переиспользует время, которое пользователь
  уже выбрал, вместо второго пикера «когда присылать дайджест», и доставляет сообщения ровно
  в момент, когда он снова готов их получать.
- **Анти-шум не урезан.** Каждое отложенное уведомление проходит тот же `DedupeGate` (дедуп по
  `itinerary_hash`, кулдаун, `daily_cap`), что и instant — никакого специального лимита «1 в
  сутки» для дайджеста нет: если за день нашлось три разных пробития порога, все три уйдут
  вместе, при условии что не упёрлись в общий `notifications_per_route_per_day`.

## Навигация: главное меню и FSM

Пользователь ходит по боту кнопками, а не командами. `/start` и `/menu` открывают главное меню
(`telegram/handlers/menu.py`), из него — добавление маршрута, список маршрутов, разовый поиск,
состояние источников и помощь. Кнопка «☰ Меню» висит на **каждой** клавиатуре, включая шаги
мастеров, где пользователя просят что-то напечатать.

Ключевое решение: обработчик `MenuAction` зарегистрирован **без фильтра по состоянию** и его
роутер включается в диспетчер первым — иначе «Меню» работало бы только на экранах, которые
случайно оказались вне FSM, а именно из середины мастера выход и нужен. Он делает
`state.clear()` без подтверждения: до последнего шага мастер ничего не пишет в БД, терять
нечего, а диалог «точно выйти?» на каждое нажатие — чистое трение.

Слэш-команды никуда не делись и регистрируются через `set_my_commands` (кнопка ☰ в клиенте
Telegram) — это второй вход для тех, кто предпочитает печатать, а не единственный.

## Один экран на чат вместо сообщения на каждый шаг

Раньше каждый шаг мастера звал `message.answer(...)`, то есть слал **новое** сообщение: создание
маршрута (откуда → куда → транспорт → даты → порог → интервал → уведомления → готово) оставляло
в чате восемь с лишним отдельных сообщений, а `/routes` рассыпал ещё по одному на маршрут. Теперь
бот держит **одно своё сообщение на чат** и переписывает его — `telegram/screen.py`.

- **Якорь — `(chat_id, message_id)` в FSM-состоянии** (ключ `screen_message_id`). Telegram
  разрешает боту править только свои сообщения, поэтому «редактировать предыдущее» физически
  означает «помнить, какое именно». Каждый рендер перезаписывает якорь.
- **Два вида триггера сходятся в одну точку.** Нажатие кнопки уже несёт сообщение бота
  (`query.message`) — оно и становится якорем, заодно перецепляя экран туда, куда человек реально
  смотрит, если он проскроллил назад и нажал старую клавиатуру. Печатный шаг несёт сообщение
  *пользователя*: якорь берётся из состояния, а напечатанная строка **удаляется** (Bot API
  прямо разрешает боту удалять входящие сообщения в приватном чате) — иначе «одно сообщение бота»
  всё равно тонуло бы в чужих репликах. Удаление — best-effort: не вышло, значит строка осталась
  висеть, экран от этого не ломается.
- **`screen_for()` снимает якорь до `state.clear()`.** Мастера чистят состояние на входе, и якорь,
  умирающий вместе с ним, означал бы новое сообщение на каждой границе потоков (меню → `/add`,
  `/search` → «Отслеживать» → `/add`) — ровно та стена сообщений, которую всё это убирает. Объект
  `Screen` держит id в памяти через очистку и перезаписывает его при следующем рендере.
- **Провал редактирования — это не ошибка, а сигнал.** `message is not modified` (одна и та же
  ошибка ввода дважды подряд) считается успехом; всё остальное (сообщение удалили, слишком старое)
  значит, что якорь мёртв — тогда уходит новое сообщение и становится новым якорем.
- **`/routes` теперь список → карточка → назад,** а не N сообщений. Карточки независимы друг от
  друга, но действуют всегда ровно над одной, так что «открыть одну, что-то поменять, вернуться
  к списку» ложится на один экран без натяжки. Пагинации нет намеренно: личный бот, маршрутов
  единицы, прокручиваемой клавиатуры хватает.
- **Уведомления о находках намеренно остаются отдельными сообщениями.** Их шлёт планировщик
  (`notify/notifier.py`), когда никакого диалога не идёт и править нечего; и уведомление о цене —
  это запись в истории, а не временный экран, затирать её следующим шагом мастера было бы потерей.
- **Каждый экран имеет одну форму** — заголовок, что уже выбрано, вопрос (`format.screen_text()`).
  Строка «что уже выбрано» (`format.describe_draft()`) появилась именно из-за этого перехода:
  раньше предыдущие ответы просто висели выше в переписке, а теперь их видно только если экран
  несёт их сам.

**Место, найденное однозначно, выбирается само.** `place_picker.ask_place_pick()` при ровно одном
совпадении не рисует клавиатуру из одной кнопки (плюс «☰ Меню»), а сразу выполняет продолжение
`on_picked` — то же самое, что делает обработчик нажатия. Продолжение передаётся колбэком, чтобы
«что происходит после выбора» не существовало в двух копиях; при нескольких совпадениях экран
выбора работает как раньше.

**Оба мастера спрашивают транспорт одним и тем же шагом.** `/search` раньше молча искал сразу
по всем режимам — `frozenset({Mode.PLANE, Mode.TRAIN})` был зашит в обработчике, и сказать
«только самолёт» было нельзя вовсе. Теперь `SearchFlow.mode` стоит там же, где `AddRoute.mode`
(после «куда», перед выбором дат), и переиспользует ту же клавиатуру `mode_picker_kb()`,
ту же `ModePick` callback-data и тот же словарь подписей `MODE_LABEL` (переехал из `handlers/add.py`
в `keyboards.py` рядом с самой клавиатурой). Значение живёт в FSM-состоянии, а не в БД —
разовый поиск ничего не сохраняет — и разворачивается в набор режимов через
`domain/places.modes_for_pref()`; `allowed_modes(route)` теперь просто вызывает её, так что
точка интерпретации `mode_pref` осталась одна на проект (§4).

**Результаты `/search` разложены по видам транспорта, а не свалены в один список.** Раньше экран
показывал пять самых дешёвых вариантов вообще — и на маршруте, где поезд дешевле самолёта, все
пять слотов занимали поезда, а цена на самолёт, ради которой человек и искал, не появлялась
вовсе. `format.select_top_itineraries()` сначала выдаёт каждой присутствующей группе её самый
дешёвый вариант, и только оставшиеся слоты раздаёт по общей цене; затем сортирует по
(группа, цена), так что группы выходят непрерывными блоками.

- **Группы:** `✈️ Авиабилеты`, `🚂 ЖД-билеты` и `🔀 Смешанные (через хаб)` — порядок тот же, что у
  кнопок выбора транспорта. Составной маршрут через хаб, где одно плечо самолёт, а другое поезд,
  не принадлежит ни одной одномодовой группе (это не «цена на самолёт» и не «цена на поезд»,
  а своя комбинированная цена) — поэтому у него отдельная секция, а не приписка к первому плечу.
  Same-mode через хаб (самолёт→хаб→самолёт) остаётся в группе своего режима.
- **Список под капотом остаётся плоским.** `SearchTrack` адресует вариант позицией в списке,
  сложенном в FSM-состояние; заголовки — это только рендер, индексация не поменялась.
- **Заголовки появляются только когда есть что разделять** — поиск «только самолёт» отдаёт тот же
  плоский нумерованный список, что и раньше.

Экран «типичных цен» из §9 плана (`route_stats` — min/median по режимам перед выбором порога)
по-прежнему не построен: `ObservationsRepo.stats()` существует, но ни один обработчик её не
зовёт. Категоризация результатов от него не зависит.

Единственный вход, который шаг выбора транспорта пропускает намеренно — «🔎 Варианты» на карточке
маршрута: пользователь уже выбрал транспорт, когда заводил маршрут, и `start_from_route()` берёт
`route.mode_pref` вместо повторного вопроса.

**Заголовок результатов теперь называет выбранный транспорт** («✈️ Самолёт», «🔀 Самолёт или
поезд» и т.д.), не только подразумевает его набором найденных вариантов — иначе поиск «только
самолёт» без поездов и «поездов правда нет на этом маршруте» выглядят на экране одинаково, а шаг
выбора транспорта легко проскочить по привычке, не заметив.

**Один запрошенный режим, вернувший ноль вариантов, теперь объясняет почему**, а не просто
выпадает из списка неотличимо от «поездов правда нет». Баг был найден живьём: поиск
Пенза→Петербург с режимом «оба» показывал только самолёты без единого слова о поездах, хотя
`/status` при этом рисовал `tutu_rail_direct`/`rzd_direct` как «отвечали». Живая проверка с самой
VDS (2026-08-19) закрыла вопрос "почему": у Пензы/Петербурга оба кода на месте
(`rzd_code`/`yandex_code` заполнены), `tutu_rail_direct.search()` для этой пары живьём вернул 108
реальных предложений — значит источник в принципе рабочий, а не "нет данных" — и подозрение упало
на бюджет интерактивного лейна: `EMPTY`/`RATE_LIMITED`/любой другой недо-`OK` статус считается
для circuit breaker здоровым (§ находки rzd_direct/tutu ниже) и обновляет `last_success_at`, а
`_render_results()` никогда не смотрел на `sources_skipped` при непустом общем списке — эта ветка
была только в «ничего не нашёл вообще». Отдельно нашёлся и почти наверняка более прямой виновник —
занятый рейт-лимит бакет мог тихо стопорить интерактивный вызов дольше 12-секундного бюджета (см.
"Занятый рейт-лимит бакет..." ниже) — теперь такой случай деградирует до `RATE_LIMITED`, а не до
молчаливого недо-ответа. `search._mode_gap_note()`
сравнивает запрошенные режимы с режимами, реально попавшими хоть в один найденный `Itinerary`
(`itinerary_modes()`), и для каждого отсутствующего режима подмешивает в `results_checked`
причины skip от адаптеров, поддерживающих этот режим (`adapter.modes`) — «🚂 ЖД-билеты: без
результатов — Туту.ру (поезда) (empty), РЖД (blocked).» Только диагностика/текст, критерии
`select_top_itineraries`/группировки не меняются.

**Живая проверка (2026-08-19, реальный поиск Пенза→Питер) сразу показала два уточнения.**
Во-первых, тот же источник появлялся в списке причин по несколько раз с одной и той же
причиной (`Яндекс.Расписания (empty)` — 4 раза) — потому что один `/search` реально дёргает
жд-адаптер несколько раз: прямое плечо плюс по разу на каждого кандидата-хаба (см.
`combiner.search_itineraries`), и каждый вызов добавляет свою запись в `sources_skipped`.
`_mode_gap_note` теперь схлопывает точные повторы `dict.fromkeys(...)`, но **сохраняет** разные
причины от одного источника (`Туту.ру (поезда) (timeout)` рядом с `Туту.ру (поезда)
(rate_limited)` в одном ответе — это не шум, а видимая конкуренция за один и тот же
rate-limit-бакет между прямым плечом и плечами через хаб, ровно то, что чинит §"Занятый
рейт-лимит бакет..." выше).

**Во-вторых, строка варианта не говорила, кто именно везёт и откуда взята цена** — только
✈️/🚂 и ✅/⚠️. `_carrier_or_source_label()` добавляет к строке результата название
перевозчика, если оно известно (confirmation-тир почти всегда знает), а если нет —
название источника (`Travelpayouts (Aviasales Data API)` и т.п.) вместо тишины: у
`travelpayouts`/`yandex_rasp` (discovery, месячная матрица без поля авиакомпании — см. докстринг
`Leg` в `base.py`) перевозчика не бывает вовсе, так что для варианта из аггрегаторского кэша
это единственный честный ответ на «откуда цена». Составной маршрут через хаб показывает оба
плеча через `/`, если они не совпадают.

**Код места (IATA/rzd_code) в текстах для человека заменён на «Название (КОД)».** Раньше
`format_deal_card` и подпись хаба в результатах поиска (`через LED`) печатали голый
трёхбуквенный код — читаемо только тому, кто коды помнит наизусть. `PlaceRef` теперь несёт
`name_ru` (`domain/combiner._place_ref()` заполняет его из `Place.name_ru`; адаптеры прокидывают
`q.origin`/`q.dest` в `Leg.from_place`/`to_place` без изменений, так что поле долетает бесплатно
до карточки уведомления), `telegram/format.place_label()` — общая точка рендера «Москва
Шереметьево (SVO)» с деградацией на голый код/id, если имени нет. `place_picker.py` (шаг выбора
города в мастерах) код в скобках **не убирает** — там это то самое место, где человек
осознанно выбирает между тёзками, а не побочный текст в результатах.

**«📋 Показать все» вместо жёсткого потолка в 5.** Изначально показываются 5 самых дешёвых (по
той же группировке, что выше), но найденный список (до `_RESULTS_MAX` = 25 — Telegram режет
сообщение на 4096 символах, честно показать буквально все 80 вариантов физически некуда)
складывается в FSM целиком при самом поиске, а не досчитывается по кнопке. `_render_results()`
переиспользуется и первым показом, и кнопкой — снова индексация `SearchTrack` остаётся плоской
и совпадает с тем, что реально нарисовано на экране.

Карточка отслеживаемого маршрута (`/routes`) несёт кнопку «🔎 Варианты» —
`search.start_from_route()` прогоняет тот же разовый поиск (§10), что и `/search`, но
предзаполненный местами и датами из самого маршрута, ничего не сохраняя. Симметрично уже
существующему мосту в обратную сторону («💾 Отслеживать» у результата `/search` → предзаполненный
`/add`) — оба направления идут через одни и те же `SearchFlow`/`AddRoute` состояния.

## Гибкие даты и бюджет запросов

`routes.date_mode` наконец используется по назначению. Мастер `/add` и `/search` предлагают
четыре варианта: точная дата, «±3 дня» вокруг опорной, произвольный диапазон и «любая дата»
(окно от 7 до `MAX_WINDOW_DAYS` дней, по умолчанию 30 — пользователь теперь вводит число сам,
раньше было жёстко зашито). Всё это сводится к `domain/dates.py::DateSelection` — той же форме,
в какой окно лежит в БД.

**Интервал опроса редактируется и после создания маршрута** — не только в мастере `/add`.
Кнопка «⏱ Интервал проверки» на карточке маршрута (`telegram/handlers/routes.py`) переводит в
`EditRoute.interval` (отдельная state-группа, не переиспользует `AddRoute.interval` — та означает
«последний шаг создания», эта — «правка существующего»), тем же диапазоном floor/ceiling, что и
при создании, и сохраняет через `RoutesRepo.set_poll_interval()`.

- **Два якоря окна, оба нужны.** Явный диапазон пользователя («с 10.09 по 20.09») хранится
  абсолютно, в новой колонке `routes.window_start_date`, и не должен уезжать; «любая дата»
  хранится смещением `window_start_offset_days` от сегодня и, наоборот, обязана ехать вперёд
  вместе с календарём. Раньше была только вторая форма, и она молча сдвигала бы любой
  осознанно выбранный диапазон каждую ночь.
- **`DatePlan` вместо голого списка дат.** `combiner.search_itineraries()` теперь принимает
  уже посчитанный бюджет: `batch_dates` (всё окно) для источников с `supports_batch_dates`
  (`travelpayouts` отдаёт месяц за один запрос — 30 дат стоят столько же, сколько одна) и
  `probe_dates` (узкий срез) для тех, кто тратит запрос на дату (`yandex_rasp`, `rzd_direct`,
  `s7_direct`). Наивный обход всего окна каждым источником — это как раз то, чего делать
  нельзя, а решает это не адаптер, а один общий слой.
- **Курсор на маршруте.** `routes.date_cursor` прокручивает срез вперёд каждый цикл опроса
  (по умолчанию 7 дат, `flex_probe_dates_per_cycle`), так что окно в 30 дней покрывается
  точечными источниками за несколько циклов, а не стоит 30 запросов каждый раз. Стоимость
  цикла не зависит от ширины окна.
- **Плечи через хаб щупают меньше дат, чем прямой рейс** (`flex_hub_probe_dates`, по умолчанию
  1). Обе половины составного маршрута должны попадать на один день, поэтому широкое окно с
  обеих сторон множит запросы квадратично ради пар, которые тут же отбрасываются. Пакетные
  источники и на плечах видят всё окно — им это ничего не стоит.
- **`/search` честно говорит, что проверил.** Синхронный поиск живёт в бюджете ~12с и физически
  не может обойти 30 дат точечными источниками, поэтому он щупает `flex_search_probe_dates`
  (3) и подписывает результат: «из окна в 30 дн. точечно проверено 3: …». Полное окно — работа
  фонового отслеживания, и это сказано прямо, а не изображено.

**Баг, который гибкие даты сделали достижимым (и который закрыт вместе с ними):** пока в
маршруте была ровно одна дата, композиция плеч через хаб могла спокойно складывать любые два
оффера. С окном оба пула плеч охватывают разные дни, и рейс 10-го склеился бы с поездом 20-го
в один «маршрут». Проверку зазора пересадки это не ловит: у discovery-офферов время —
подставная полночь, и та проверка намеренно не запускается (см. историю с `compose()` выше).
Отсюда `_dates_composable`: второе плечо отправляется в тот же день или на следующий, иначе
пара не рассматривается.

`combiner.search_itineraries()` — общая точка входа для "как добраться из A в B", принимает
весь набор разрешённых режимов сразу (не по одному вызову на режим). И `scheduler.worker`, и
`telegram/handlers/search.py` (`/search`) вызывают её же, различаясь только `SearchOpts`; логика
фильтрации адаптеров и freshness gate не дублируется.

**Занятый рейт-лимит бакет в интерактивном лейне теперь тоже под бюджетом.**
`RateLimiter.acquire()` (`adapters/ratelimit.py`) ждёт `min_interval_s` с прошлого запроса к
источнику *до* того, как адаптерный `asyncio.timeout(timeout_s)` вообще начинает отсчёт (см.
порядок в `registry.search()`) — свой собственный докстринг у `acquire()` давно объявлял
`max_wait_s` именно под интерактивный лейн, но ни один вызывающий код его не передавал. На
практике это значило: если тот же источник только что дёрнул планировщик (или другой конкурентный
`/search`), интерактивный поиск мог тихо простаивать на ожидании бакета вплоть до полного
`min_interval_s` источника (15с у `tutu_rail_direct`, 20с у `rzd_direct`) — дольше заявленного
`interactive_l1_deadline_s` — не роняя запрос, а просто делая его медленнее и позже видимого
"⏳ Ищу…" молча. `_search_leg()` теперь передаёт `bucket_wait_s=opts.deadline_s` именно в
интерактивном лейне — источник, чей бакет занят дольше отведённого бюджета, вместо тихого
ожидания сразу деградирует до `RATE_LIMITED` (виден в `_mode_gap_note`, §10), а не растягивает
ответ бота. Лейн планировщика поведения не меняет — там ждать некому, `bucket_wait_s=None`.

**Веер адаптеров внутри одного плеча — параллельный.** `_search_leg()` спрашивает все подходящие
источники одновременно (`asyncio.gather`), а не по очереди. Реальный потолок сетевой активности
задаёт не этот цикл, а сам реестр: семафоры `http_concurrency_global`/`http_concurrency_per_source`,
пейсинг `ratelimit.py` и circuit breaker — и всё это ключуется по `adapter.id` (отдельный
Semaphore/Lock/бакет на запись), поэтому одновременные вызовы к *разным* адаптерам не делят
изменяемое состояние вовсе. Последовательность здесь не давала никакой дополнительной
безопасности — только стоимость плеча, равную сумме таймаутов всех источников вместо максимума.
Два следствия, за которыми надо следить: результаты `gather` разбираются в порядке регистрации
адаптеров (а не в порядке ответа), чтобы `sources_used`/`sources_skipped` были воспроизводимы;
и используется `return_exceptions=True` — не из перестраховки на невозможный случай, а потому
что голый `gather` отменяет все ещё летящие запросы при первом же исключении, то есть
параллельность превращает баг одного адаптера в потерю уже собранных офферов остальных, чего
последовательный цикл сделать не мог.

**Выбор хаба смотрит на географию, а не только на популярность.** Реальный баг: `hub_candidates_near`
ранжировал кандидатов одним лишь `popularity DESC` в пределах страны — а в живом сиде Москва (90)
стоит намного выше всех, следующий эшелон (70) это по сути шум (Тура, Кепервеем — крошечные
аэропорты, а не Самара с Екатеринбургом). При `MAX_HUBS_DEFAULT = 2` это означало, что **любому**
маршруту предлагались Москва плюс один случайный далёкий филлер, независимо от того, где он
физически находится. Хардкода города не было, но эффект от него неотличим.

Колонки `places.lat/lon` лежали в схеме с миграции 001 и не читались нигде. Теперь SQL только
*фильтрует* (страна, не вырожденный кандидат), а выбор делает `rank_hub_candidates`
(`db/repo_places.py`) поверх `domain/geo.py`:

- **Крюк** — `haversine(origin, hub) + haversine(hub, dest) - haversine(origin, dest)`, всегда ≥ 0.
  Хаб, реально лежащий на линии, получает ~0, отставленный вбок — всю величину объезда.
- **Отсечка** — крюк больше, чем `max(500 км, длина прямого перелёта)`, выбрасывает кандидата
  совсем. Плоская добавка нужна коротким плечам (на 339 км Пенза→Самара никакой хаб в пределах
  339 км крюка не поможет), а коэффициент 1.0 — верхняя граница того, где хаб с реальным
  инвентарём ещё может выиграть по цене.
- **Ранжирование внутри отсечки** — `popularity - крюк_км / 10`, то есть 10 км крюка стоят одного
  пункта популярности. Откалибровано по разбросу живого сида (региональные города 50–60,
  Москва 90): Москва по-прежнему выигрывает там, где действительно лежит на пути
  (Пенза→Калининград, крюк 40 км), а на Пенза→Сочи её объезд в 779 км стоит 78 пунктов, и Самара
  (514 км) идёт следом — оба хаба пробуются. На Екатеринбург→Сочи Самара (крюк 17 км) обгоняет
  Москву напрямую. Тура выпадает везде.
- **Без координат — не победа по умолчанию.** Кандидат без `lat/lon` ранжируется строго позади
  всех посчитанных, как филлер; если координат нет у самой точки отправления/назначения, считать
  нечего вовсе и порядок честно деградирует до прежнего популярностного.

**Маршруты через хаб:** если `max_hops >= 1`, комбинатор берёт до 2 кандидатов-хабов
(`places_repo.hub_candidates_near`, по умолчанию — динамически, без хардкода городов), для
каждого ищет оба плеча независимо (`origin→hub`, `hub→dest`) по каждому режиму, и комбинирует
через `domain/transfers.py`. Смешивать режимы необязательно — same-mode через хаб (самолёт→хаб→самолёт)
тоже пробуется, не только миксы. Результат — `Itinerary` с 1 плечом (прямой) или 2 (через хаб),
отранжированные по итоговой цене с учётом стоимости пересадки. `dealer`/`notifier`/`format`
теперь оперируют целым `Itinerary`, а не одним `Offer`, поскольку оба плеча составного маршрута
могут прийти от разных источников с разным tier/confidence.

Кнопка «Отслеживать» под результатами `/search` не сохраняет отдельную сессию (`search_sessions`
из плана — Phase E), а просто переносит уже известные origin/dest/режим/дату в FSM-состояние
мастера `/add`, пропуская повторный ввод.

**Два реальных бага, найденных живым end-to-end тестом (маршрут через хаб на реальных городах),
не ревью кода:**
1. `compose()` считал зазор пересадки между двумя `discovery`-офферами без известного времени
   (у Travelpayouts только дата, время — заглушка "полночь") как буквально 0 минут между двумя
   одинаковыми полуночами → каждая связка в тот же день ложно браковалась как "слишком короткая
   пересадка". Теперь проверка зазора/длительности запускается только если оба конца реально
   знают время; иначе — не отвергается и не подтверждается, честно неизвестно.
2. `registry` считал `EMPTY` (источник ответил нормально, просто ничего не нашёл) отказом для
   circuit breaker — маршрут с законно скудными результатами (как оказалось, ровно случай
   Яндекс.Расписаний без цен) мог словить открытие цепи после 5 пустых-но-успешных запросов.

## Адаптеры источников

Каждый источник цен — класс, реализующий протокол `SourceAdapter` (`adapters/base.py`):
`search()` никогда не бросает исключение, вся политика retry/backoff/circuit-breaker/кэша
живёт в общей обёртке реестра (`adapters/registry.py`), а не в самом адаптере. Добавление
нового источника — один новый файл + одна строка регистрации.

**Таймауты: у каждого адаптера свой честный потолок, а не общий дедлайн сверху.**
`total_timeout_s` теперь считается из реальной формы работы источника —
`adapters/base.probe_dates_total_timeout_s(per_date_s, setup_s=…)`: стоимость одной даты,
умноженная на `flex_probe_dates_per_cycle` (7), плюс разовая подготовка перед циклом. Значения
не выдуманы: aeroflot/pobeda/tutu_rail 140с (7 POST по 20с), azimuth 120с (+ `init`-вызов),
tutu_avia 180с (+ 2 GET к suggester), yandex_rasp 105с, rzd 252с (у него дата — это не один
запрос, а POST плюс до 14 поллингов), s7 270с (+ 2 lookup'а и один браузерный solve;
у него `total_timeout_s` — атрибут экземпляра, потому что `solver_timeout_s` задаётся в
конструкторе). Число берётся из конфига, а не хардкодится, чтобы потолок и ширина цикла не
разъезжались — именно это разъезжание и оставило все confirmation-адаптеры с плоскими 60с.

Разрешение таймаута в `registry._resolve_timeout_s()` теперь зависит от полосы. Раньше было
`deadline_s or adapter.total_timeout_s` — любой непустой дедлайн вызывающего побеждал молча, и
плоские 90с планировщика выбрасывали уже собранные офферы адаптера просто потому, что кончились
часы. Теперь: в полосе `scheduler` дедлайн может только **поднять** потолок адаптера, но не
опустить ниже его собственного (фоновый опрос никто не ждёт, обрывать его — чистая потеря);
в полосе `interactive` — наоборот, дедлайн жёсткий, потому что `/search` идёт под
`interactive_l1_deadline_s` (12с) при живом пользователе, а confirmation-адаптеры с этого пути
достижимы. Полоса передаётся через `SearchOpts.lane`, `SearchOpts.deadline_s` по умолчанию
`None` («пусть решает сам адаптер»), и `scheduler/worker.py` больше не передаёт дедлайн вовсе.
Прежнее опасение «N адаптеров × большой потолок = неограниченный цикл» стало меньше, а не
больше: веер параллельный, плечо стоит примерно максимум потолков, а не их сумму.

Два тира: `discovery` (дёшево, пакетно, может быть устаревшим) и `confirmation` (узкий live-запрос
к конкретному сайту перевозчика). Сейчас подключены `travelpayouts` (авиа-цены, discovery),
`yandex_rasp` (жд-расписания, discovery), `rzd_direct` (реальные жд-цены, confirmation, сейчас
забанен на боевой VDS — см. находку ниже), `tutu_rail_direct` (реальные жд-цены через
внутренний JSON-эндпоинт tutu.ru, confirmation — второй, независимый жд-источник, см. находку
ниже), `s7_direct` (реальные цены S7, confirmation — статус не подтверждён при повторной
проверке, см. находку ниже), `aeroflot_direct` (реальные цены Аэрофлота и
**России** через общий инвентарь группы, confirmation — см. находку ниже) и `azimuth_direct`
(реальные цены Азимута, confirmation — региональный юг России), `pobeda_direct` (реальные
цены Победы, confirmation — обходит VPN-детектор через домашний прокси, см. находку ниже) и
`tutu_avia_direct` (реальные цены через внутренний API tutu.ru, confirmation — многоперевозочная
подстраховка на случай отсутствующего прямого адаптера, см. находку ниже).
Red Wings, Smartavia, Ural Airlines, Utair не построены: Utair банит датацентровые IP на
сетевом уровне и держит за ним Qrator JS-челлендж (тот же класс, что ServicePipe у S7 — не
решается сменой IP, нужен реальный браузер); Red Wings и Smartavia доступны, но их HAR-снимки
не захватили запрос, который создаёт поиск (нужен повторный HAR именно с момента нажатия
«Найти», не с уже открытых результатов); Ural Airlines и Yakutia ещё не присылали HAR вовсе.

**Находки при живой проверке (не из документации — проверено запросами к реальным API):**
- Travelpayouts `v2/prices/month-matrix` не даёт ни авиакомпанию, ни номер рейса, ни точное
  время — только дату, цену, число пересадок и суммарную длительность. Поэтому
  `Leg.carrier`/`number`/`arrive_utc`/`tz` опциональны (`time_precision` показывает честно, когда
  время — просто дата), а адаптер отбрасывает рейсы с пересадками (`number_of_changes > 0`) —
  достраивать их из этих данных означало бы выдумывать хаб и перевозчика.
- У `stations_list` Яндекс.Расписаний нет поля IATA вообще, а `system=iata` работает только для
  аэропортов, не для городов/поездов — поэтому `yandex_code` для городов сопоставляется по
  названию (`seed_places.py`), не по коду.
- Для реальных поездов Москва→Питер (57 найдено на дату, много дат и с/без фильтра
  `transport_types` проверено) — у 0 из этих сегментов есть цена через бесплатный ключ Яндекс.
  Расписаний. При этом автобусные сегменты через тот же ключ цену отдают — то есть дело не в
  параметрах запроса, а конкретно в жд-тарифах, закрытых от этого тира доступа.
- `pass.rzd.ru` (неофициальный эндпоинт, тот же, что использует сам сайт РЖД) реально отдаёт
  цены — проверено вживую: двухшаговый RID-флоу (`POST` поиска → `{"result":"RID","RID":N}` →
  поллинг того же URL с этим `RID` до `{"result":"OK","tp":[...]}`) резолвится за ~3с, без капчи,
  с полными тарифами по классам вагонов. Запросно-ответная форма сверена с эталонной реализацией
  `github.com/devbis/aiorzd`, документирующей тот же флоу. Нет ни официальной документации, ни
  bulk-дампа станций (в отличие от Яндекса) — коды городов достаются по одному через
  `/suggester` при сиде (`seed_places.py`). Время прилёта/отправления приходит без UTC-смещения и
  без указания станционного часового пояса — принято допущение "домашнее время РЖД = Москва"
  (задокументировано прямо в `rzd_direct.py`), а не строгая таблица часовых поясов по станциям.
- `ibe.s7.ru` (реальный поиск S7) закрыт JS-челленджем от антибот-вендора ServicePipe — стартовый
  запрос без пройденного челленджа отдаёт HTML-заглушку со скриптом-лоадером вместо страницы,
  без него ни `execution`/`ibe_conversation` (id Spring Webflow-сессии), ни рабочие куки не
  получить. Разобран сам челлендж-скрипт (`checkjs`, 347КБ, обфусцирован) — реально трогает
  `canvas.getContext`/`navigator.webdriver`, то есть требует настоящего браузерного окружения;
  голый JS-движок без DOM не проходит. Найденный реальный эндпоинт с ценами —
  `POST https://ibe.s7.ru/air` с `_eventId=getExtendedSearchResult`; связь цены с рейсом —
  `flightOption.solutions[fareFamily].pricing.total.salePrice.amount` (проверено на живом
  ответе: `flightOptionId` внутри `solutions[...]` совпадает с `id` самого `flightOption`) —
  отдельная top-level структура `tariffAlternatives` похожа по форме, но не привязана к
  конкретному рейсу однозначно, использовать её для цены было бы ошибкой.
- **`patchright`-браузер (наш собственный ephemeral-фолбек) живьём проверен и не проходит
  ServicePipe** — протестировано на трёх разных сетях (домашний IP, VPN, сама VDS) — во всех
  трёх случаях мгновенный `403 Forbidden`, челлендж даже не показывается. Значит блокируется не
  IP/сеть, а сам факт CDP-управляемого браузера — независимо от анти-детект патчей patchright.
  При этом обычный, не автоматизированный Chrome пользователя челлендж проходит стабильно
  (подтверждено живым HAR с реальными ценами). Вывод: код `browser_solver.py` остаётся в проекте
  как резервный путь (вдруг пригодится для источника со слабее защитой, или ServicePipe
  когда-нибудь пропустят патчи по-другому), но **сейчас он не является рабочим механизмом обхода
  для S7** — реальный obход ниже.
- **Рабочий обход — ручная передача сессии.** Раз только настоящий браузер реально проходит
  челлендж, `/s7_session` (админ-команда, `telegram/handlers/admin.py`) принимает экспорт кук
  (JSON из расширения типа Cookie-Editor, либо сырую строку `a=b; c=d`) после того как админ
  один раз сходил на `ibe.s7.ru` в своём обычном браузере, и кладёт их в `SessionsRepo` под
  ключом `s7_direct` — тот же кэш, которым при успехе воспользовался бы browser-solver.
  `cfidsw-s7-ibe` (похоже, основной трастовый токен) в живом захвате имел срок жизни около года —
  значит это не ежедневная рутина, а редкое обслуживание по факту (`s7_direct` вернёт `BLOCKED`,
  когда сессия протухнет — это сигнал админу освежить).
- **Повторная проверка (2026-08-18) — статус `s7_direct` как рабочего источника не подтверждён,
  найдено две отдельных проблемы.** Во-первых, `browser_solver.py` при повторном живом запуске не
  прошёл ServicePipe вовсе — не показал челлендж-страницу, как раньше, а сразу получил жёсткий
  `403 Forbidden` со страницей "If you are not a bot, please copy the report" (текущий IP теста
  зафиксирован в теле ответа). Значит либо детект `patchright` ужесточился, либо репутация тестовой
  сети упала — в любом случае прежний вывод "патчи patchright не проходят, но реальный Chrome
  проходит" сейчас не переподтверждён живым тестом, только зафиксирован как исторический факт.
  Во-вторых, и важнее: свежий HAR (`ibe.s7.ru.har`, реальная браузерная сессия) показывает, что
  **каждый** `POST /air` с `_eventId=getExtendedSearchResult` (и вообще любой вызов на этот URL)
  несёт два заголовка — `x-gib-fgsscw-s7-ibe` и `x-gib-gsscw-s7-ibe` — значения которых **разные
  на каждый из 11 запросов сессии** (не разные один раз при заходе, а буквально на каждый вызов).
  Это похоже на подписанный клиентский токен антибот-вендора (GlobalDots/аналог), вычисляемый
  JS на лету — а не на статичный per-session секрет. Адаптер (`s7_direct.py`) эти заголовки вообще
  не генерирует и не пробрасывает из решённой сессии — вся конструкция "дешёвый путь = решить
  челлендж один раз, дальше просто переиспользовать куки" (см. докстринг класса) может быть
  неполной: даже с валидными куками реальный ценовой запрос без этих per-request заголовков может
  просто отклоняться бэкендом. Не проверено эмпирически до конца (нужен рабочий browser-solver,
  чтобы получить валидные куки и проверить запрос без/с заголовками раздельно) — фиксируется как
  открытый вопрос, а не закрытый баг. **Практическое следствие: переносить эту же архитектуру
  ("решить один раз, дальше по кукам") на ЮТэйр не стоит, пока не выяснено, работает ли она вообще
  для S7** — см. README "Запланировано, ещё не построено".
- **`rossiya-airlines.ru` недоступен для скрейпинга напрямую — но не нужен.** Прямой домен не
  отвечает ни с VDS, ни через VPN (Франция): TCP+TLS handshake проходят, дальше тишина, 0 байт —
  похоже на блокировку по репутации IP на сетевом уровне, не на TLS-фингерпринт (тот же паттерн
  что и с TLS-рукопожатием для `www.aeroflot.ru`, только на уровень ниже — там `curl_cffi`
  спасает, здесь нет). Обходной путь нашёлся сам: `www.aeroflot.ru`'s
  `POST /sbe/flight-search/api/web/v1/flight/search` — общий поисковый бэкенд группы
  «Аэрофлот» — реально продаёт билеты России под своим кодом (`marketing_airline_code: SU`),
  но с `operating_airline_code: FV` (Россия) как фактического перевозчика. Живой поиск
  Санкт-Петербург→Сочи вернул 13 из 13 вариантов с `FV` — то есть на многих внутренних
  маршрутах Аэрофлот и есть Россия. Антибот здесь — только TLS-фингерпринт (обычный `curl`
  получает `503` со страницей WAF, `curl_cffi` с `impersonate="chrome"` проходит без кук и
  без сессии), тот же класс, что у `rzd_direct`/`travelpayouts`, не JS-челлендж как у S7.
  `aeroflot_direct.py` берёт `operating_airline_name` как `Leg.carrier`, а не маркетинговый
  бренд — иначе Россия была бы невидима в собственных данных. **Отдельно проверено:** серия
  запросов подряд без пауз (несколько штук за секунды) ловит временную блокировку — WAF-страница
  вместо JSON, — но она сама снимается примерно за 45с и не зависит от конкретного маршрута
  (один и тот же LED→AER то блокировался, то нет). Это троттлинг по частоте, не по IP навсегда
  и не по TLS-отпечатку. `rate_limit` адаптера поднят до 15с (было 10) с тем же запасом, что у
  `s7_direct` — на практике (confirmation-тир, по одному запросу за раз, не пачками) не должно
  задевать этот порог вообще.
- **РЖД реально банит VDS на сетевом уровне** (`403 Forbidden` на всех `pass.rzd.ru`-эндпоинтах,
  не только на `/suggester`) — подтверждено сравнением: с локальной (не-датацентровой) сети всё
  открывается чистым JSON, с VDS — `Forbidden` с указанием IP прямо в теле ответа. Проверено на
  прокси через отдельную VPN-подписку с ротацией IP (три локации — Россия, Германия, США) —
  ни одна не помогла. **Отдельно проверено и через настоящий резидентский IP** (домашний
  Tailscale-релей, см. ниже) — тоже `403`. Значит для РЖД это не бан конкретного IP/класса
  адресов вовсе, а что-то ещё (возможно старый бан по факту нагрузки во время сидирования
  `rzd_code`, см. §"Адаптеры источников" выше) — открытый вопрос, `rzd_direct` остаётся
  рабочим кодом, ждущим, когда блокировка снимется сама.
- **Найденный попутно баг: `_post()` схлопывал 403 в тот же общий "error", что и обрыв
  соединения/парсинга**, поэтому реальный сетевой бан классифицировался как `UPSTREAM_ERROR`,
  а не `BLOCKED` — статус в БД/`/status` был технически "не ОК" (счётчик ошибок рос как надо),
  но причина называлась неверно. `_post()` теперь возвращает и тело, и HTTP-статус, `_search_day`
  маппит именно `403` в `"blocked"` отдельно от прочих сетевых сбоев.
- **`/status` показывал «отвечал N назад» для источника, который прямо сейчас не отвечает.**
  `last_success_at` пишется один раз и не тухнет — если РЖД или Туту.ру когда-то ответили
  успешно, а потом начали стабильно фейлить (5+ подряд), строка всё равно рисовала старую метку
  времени вместо счётчика текущих ошибок, и рядом с ❌/⚠️ это читалось как «более-менее живой».
  `telegram/handlers/status.py::render_status()` теперь при `consecutive_failures > 0` ведущим
  показывает именно счётчик ошибок, а старую метку успеха — только в скобках справочно.
- **`offers-api.tutu.ru` — второй, независимый источник реальных жд-цен, найден в свежем HAR
  (`www.tutu.ru.har`).** `POST /railway/offers` — тот же внутренний JSON-эндпоинт, который дёргает
  собственный фронтенд tutu.ru при поиске, без какой-либо авторизации: живьём проверено со
  свежесгенерированными случайными `searchId`/`sessionId`/`pageId` (без кук вовсе) — `200 OK`,
  полные реальные тарифы. Параметры `departureStationCode`/`arrivalStationCode` — это буквально
  коды станций РЖД (Экспресс-3): совпадают один в один с кодами, которыми `rzd_direct.health_check`
  зондирует Москва→Питер (`"2000000"`/`"2004000"`), так что `tutu_rail_direct.py` переиспользует
  уже существующий `places.rzd_code` напрямую, без нового справочника мест. Ответ приходит как
  массив из 1+ JSON-объектов ("чанков" по мере ответа разных перевозчиков) с пересекающимися, но
  не идентичными наборами предложений (часть исчезает между чанками — видимо, места кончаются
  прямо во время поиска) — `_merge_chunks` объединяет предложения и справочники (`routes`/
  `segments`/`carriers`/`voyages`) по всем чанкам, чтобы не терять то, что было в более раннем
  снимке. Часть вариантов цены приходит с `price.type == "absent"` (amount=0, тип действия
  `PRE_ORDER`/`NOTIFICATION`) — это места по listу ожидания, не реальный тариф; адаптер
  отфильтровывает такие варианты и пропускает предложение целиком, если реальной (`"exact"`) цены
  не осталось вовсе. В отличие от `rzd_direct`, время прибытия/отправления приходит с настоящим
  UTC-смещением на каждый сегмент (`"2026-08-19T22:15:00+03:00"`) — не нужно допущение "всё время
  московское".
- **`offers-api.tutu.ru/avia/offers/v2` — авиа-версия того же API, построена как `tutu_avia_direct`.**
  Тот же формат ответа/тот же анти-абсент фильтр, что и у жд-версии, но резолюция места другая:
  жд переиспользует `rzd_code`, авиа своего готового id в БД не имеет, поэтому город резолвится
  живым текстовым запросом к `suggester-avia.tutu.ru?name=<IATA>` (проверено: `name=SVX` находит
  ровно ту suggestion, где `city.code == "SVX"`) — тот же паттерн "резолвить и закэшировать в
  памяти", что уже есть у `s7_direct._resolve_location_id`, новой колонки в БД не понадобилось.
  Carrier берётся по `type: "operating"` сегмента, а не `"marketing"` — тот же принцип, что у
  `aeroflot_direct` (иначе кодшер Россия/Аэрофлот был бы невидим под чужим брендом), хотя в живом
  ответе оба типа обычно совпадают. Ценно как многоперевозочная подстраховка: один эндпоинт
  агрегирует сразу нескольких перевозчиков, включая тех, для кого своего прямого адаптера ещё нет
  (Red Wings, Smartavia, Ural, Yakutia — см. README).
- **Победа и ЮТэйр блокируют иначе — и решаются по-разному.** Победа возвращает статическую
  403-страницу текстом «ваш IP-адрес не прошёл проверку, если используете VPN — выключите» —
  явный VPN/датацентр-детектор по репутационной базе, а не что-то специфичное для конкретного
  IP: три VPN-локации не прошли, а **настоящий резидентский IP (домашний Tailscale) прошёл
  сразу**, живой запрос LED→SVX вернул реальные тарифы. `pobeda_direct.py` поэтому единственный
  адаптер в ростере с собственным `proxy_url` — `tools/home_socks5_relay.py` запускается на
  домашнем компе админа (не на VDS), слушает только на Tailscale-интерфейсе (недостижим извне
  tailnet), и `pobeda_proxy_url` в `config.yaml` указывает на него. ЮТэйр — другой случай: та же
  сетевая блокировка снимается тем же резидентским IP (403 → 401), но за ней стоит настоящий
  JS-челлендж от **Qrator** (`/__qrator/qauth.js`) — тот же класс защиты, что ServicePipe у S7
  (нужен реальный браузер, смена IP не решает), поэтому адаптер под ЮТэйр не построен.
- **`aeroflot_direct` тоже начал банить датацентровый IP VDS — не сразу, спустя время после
  первой проверки.** Живой докстринг адаптера датирован 2026-08-17 и тогда работал напрямую;
  к 2026-08-18 WAF стал отдавать 200 OK с HTML-страницей «Доступ к сайту временно ограничен
  владельцем веб-ресурса» вместо JSON — код видел статус 200, пытался распарсить JSON,
  падал на `resp.json()` → трактовал как `upstream_error`, не `blocked` (внешне неотличимо
  от честного сбоя API, пока не посмотришь тело ответа). Решилось так же, как у Победы —
  выход через другой IP — но источник другой: не домашний Tailscale-релей, а **второй
  xray-outbound прямо на самой VDS** (`ru-bridge`, российский bridge-сервер, уже был
  настроен в `/etc/xray/config.json` под тегом `test-in` → `127.0.0.1:10809`, просто не был
  подключён ни к одному адаптеру). Живой запрос через него вернул настоящий JSON-ответ API
  (422 ValidationError по недостающему полю — то есть реальный код Аэрофлота, не WAF-страница).
  `aeroflot_proxy_url` в `config.yaml` — тот же паттерн, что `pobeda_proxy_url`, но без
  внешней зависимости от домашнего компа: прокси живёт локально на VDS.
- **`azimuth_direct` — JSON-RPC без антибота вообще, но с неочевидной сессией.** `booking.azimuth.ru/rpc/tsh`
  (Sirena-Travel-стиля батч-вызовы `[["method", params], ...]`) отвечает `curl_cffi` без кук и
  без проблем, но `get-availability` без предварительного `init`-вызова отдаёт честную ошибку
  `"no partner information (call INIT)"`. Ключевая находка: токен сессии приходит не в cookie и
  не в теле ответа, а в HTTP-заголовке `Authorization` (`bearer …`) самого `init`-ответа — его
  нужно прочитать из заголовков и передать обратно как `Authorization` на следующий вызов.
  Живой `init` → `get-availability` на LED→MOW вернул реальные тарифы с первой попытки.

## Ключевые решения и почему

- **SQLite вместо сервера БД** — нулевой холостой RAM на боксе с 1GB.
- **Headless-браузер — только как редкий изолированный фолбек, не основной путь.** Правило
  сужено (было "никогда"): `s7_direct` всегда сначала пробует дешёвый путь — обычный HTTP-запрос
  (`curl_cffi`, TLS-отпечаток Chrome) с закэшированными антибот-куками. Только если этот путь
  заблокирован, в отдельном подпроцессе поднимается `patchright`/chromium (`solver/`) — но против
  ServicePipe (S7) этот путь на практике не проходит (см. находки выше) — реальный источник кук
  сейчас — ручная передача через `/s7_session`. Подпроцесс-фолбек всё равно остаётся в коде: он
  дешёвый, ничего не ломает, и может сработать против источника со слабее защитой. Если сайт
  защищён по TLS-отпечатку без JS-челленджа — обход через `curl_cffi`, браузер вообще не нужен
  (см. `rzd_direct`/`travelpayouts`, им браузер не требовался).
- **Python, не Go/Node** — узкое место не CPU (I/O-bound, вежливые паузы к источникам), а скорость
  добавления нового адаптера; для реверс-инжиниринга сайтов у Python богаче экосистема и примеры.
- **Секреты vs тюнинги разделены** — `.env` только для токенов/ключей, `config.yaml` для лимитов
  (кол-во воркеров, HTTP-конкурентность, TTL кэша и т.д.) — поднять лимиты на новом VDS = поменять
  конфиг, не код.
- **Аварийная остановка только для владельца** — `/stop` проверяет `ADMIN_TG_ID`; systemd юнит на
  `Restart=on-failure`, чтобы чистая остановка не перезапускалась сама. cgroup-лимиты (`MemoryMax`)
  гарантируют, что бот не заберёт ресурсы у Tailscale/SSH на той же VDS вне зависимости от команд.
- **2GB файловый swap на NVMe поверх штатного zram** — на боевой VDS кроме zram (~478MB,
  сжатие в RAM) добавлен настоящий файл подкачки на диске (`/swapfile`, приоритет ниже zram —
  используется как второй эшелон, когда zram исчерпан), в `/etc/fstab` — переживает перезагрузку.
  NVMe достаточно быстрый, чтобы это было реальной, а не только теоретической страховкой от
  редких всплесков памяти (например ephemeral browser-solver), почти бесплатно по диску (15GB
  бюджет, задействовано меньше половины).
- **Заложена, но не построена generalization под ЖД-конкурентов/автобусы/другие страны** —
  `Mode` enum, поле `countries` у адаптера, таблица пересадок с fallback по стране — см. план §1/§5/§8.
- **`api.telegram.org` недоступен с российского VDS напрямую** (заблокирован на уровне сети —
  подтверждено `curl`-таймаутом), из-за чего бот падал в рестарт-луп на голом хостинге. Решение —
  только сессия бота к Telegram идёт через прокси (`telegram_proxy_url` в `config.yaml`,
  `aiohttp-socks`/`AiohttpSession(proxy=...)` в `telegram/bot.py`); все адаптеры-источники
  (`travelpayouts`, `yandex_rasp`, `rzd_direct`, `tutu_rail_direct`, `s7_direct`) остаются на прямом соединении —
  им блокировка не касается, а лишний прыжок через прокси только замедлил бы их. На VDS прокси —
  локальный `xray-core` (`systemd`-юнит `xray`, слушает только `127.0.0.1:10808`), поднимающий
  VLESS Reality туннель до внешнего сервера; бот обращается к нему как к обычному SOCKS5.

прогоном на реальных API — фиксирую здесь как метод: юнит-тесты на моках не увидели бы эту
проблему, поскольку баг был именно в том, *какие* данные реально отдаёт источник.

Реальный баг, пойманный раньше интеграционным тестом: `notifications_sent.sent_at` и
`users.created_at` писались через `datetime('now')` SQLite (другой формат строки, без смещения),
а читались через `datetime.fromisoformat()` — молча ломало cooldown и дневной лимит. Переписаны
на явный `datetime.now(timezone.utc).isoformat()`, как везде в проекте.
