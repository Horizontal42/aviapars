# Архитектура

Полное обоснование решений и историю ревизий — см. [plans/squishy-scribbling-dawn.md](plans/squishy-scribbling-dawn.md).
Этот файл — сжатый снимок текущей структуры, обновляется вместе с кодом.

## Что делает проект

Telegram-бот, работающий на одном процессе (VDS 1 vCPU / 1GB RAM / 15GB disk, Ubuntu 24.04):
опрашивает источники цен по маршрутам, заданным пользователем через бота (`/add`), и уведомляет,
когда цена падает ниже заданного порога. Живой ходовой скелет работает end-to-end (route →
combiner → validator → dealer → notifier → Telegram), включая **маршруты через хаб** (например,
Екатеринбург→Москва→Сочи) — комбинатор ищет оба плеча отдельно и сравнивает с прямым рейсом по
итоговой цене. Проверено вживую на реальных API. Подтверждающие адаптеры авиакомпаний (Rossiya,
S7 и т.д.) и реальные цены на поезда — ещё нет (см. "Известное ограничение" в README); ниже
описано только то, что реально существует в коде сейчас.

## Структура каталогов

```
src/aviapars/

├── db/                          # engine, миграции, репозитории, типизированные модели
├── telegram/
│   ├── bot.py                   # Bot/Dispatcher, регистрация роутеров
│   ├── handlers/                # start, add, search (оба FSM-мастера), routes, status, admin
│   ├── place_picker.py          # общий виджет выбора места — переиспользуют add и search
│   ├── keyboards.py, states.py, format.py
├── scheduler/
│   ├── tick.py                  # цикл раз в 60с: due-маршруты + отложенные notify-задачи
│   └── worker.py                # обработка одного маршрута
├── adapters/
│   ├── base.py                  # протокол SourceAdapter, Offer/Leg/SearchQuery
│   ├── registry.py               # rate-limit + circuit-breaker + кэш + таймауты — единая обёртка
│   ├── ratelimit.py, circuit.py, cache.py
│   ├── travelpayouts.py          # авиа-цены (discovery, кэш агрегаторов)
│   └── yandex_rasp.py            # расписания поездов (цен пока нет — см. README)
├── domain/
│   ├── combiner.py                # единая точка входа поиска: прямые рейсы + маршруты через хаб
│   ├── transfers.py               # политика пересадки (мин. время, стоимость) — пока только дефолты
│   ├── validator.py, dealer.py, places.py
└── notify/                       # notifier.py (форматирование/дедуп/тихие часы), dedupe.py

data/
├── migrations/                     # 001 — вся схема; 002 — уникальный индекс (kind, iata) для сида
└── seed_places.py                  # 1) дамп городов/аэропортов Travelpayouts (578 строк RU);
│                                      2) при наличии YANDEX_RASP_API_KEY — сопоставляет города
│                                         с yandex_code по названию (296/335 совпало); идемпотентно

tests/fixtures/                     # записанные реальные ответы источников
```

`health/` в дереве пока пустой — circuit-breaker живёт в `adapters/circuit.py` и персистится
через `db/repo_health.py`, отдельный модуль не понадобился.

## Поток данных (то, что реально есть)

```
/add → routes (БД) → scheduler.tick (раз в 60с) → worker.process_route
                                                        → combiner.search_itineraries()
                                                        → validator.freshness_gate
                                                        → dealer.crosses_threshold
                                                        → notifier.send_deal → Telegram
```

`scheduler/tick.py` обрабатывает due-маршруты последовательно в цикле, а не через отдельный
пул воркеров с очередью `jobs` — с одним зарегистрированным адаптером это лишняя сложность.
Таблица `jobs` пока используется только для одного случая: отложенная доставка уведомления,
если у пользователя тихие часы (`kind='notify'`). Полная схема планировщика с пулом воркеров —
на будущее, когда число источников/маршрутов сделает последовательную обработку медленной.

`combiner.search_itineraries()` — общая точка входа для "как добраться из A в B", принимает
весь набор разрешённых режимов сразу (не по одному вызову на режим). И `scheduler.worker`, и
`telegram/handlers/search.py` (`/search`) вызывают её же, различаясь только `SearchOpts`; логика
фильтрации адаптеров и freshness gate не дублируется.

**Маршруты через хаб:** если `max_hops >= 1`, комбинатор берёт до 2 кандидатов-хабов
(`places_repo.hub_candidates_near`, по умолчанию — динамически, без хардкода городов), для
каждого ищет оба плеча независимо (`origin→hub`, `hub→dest`) по каждому режиму, и комбинирует
через `domain/transfers.py`. Смешивать режимы необязательно — same-mode через хаб (самолёт→хаб→самолёт)
тоже пробуется, не только миксы. Результат — `Itinerary` с 1 плечом (прямой) или 2 (через хаб),
отранжированные по итоговой цене с учётом стоимости пересадки. `dealer`/`notifier`/`format`
теперь оперируют целым `Itinerary`, а не одним `Offer`, поскольку оба плеча составного маршрута
могут прийти от разных источников с разным tier/confidence.

Кнопка «Отслеживать» под результатами `/search` не сохраняет отдельную сессию (`search_sessions`
из плана — Phase E), а просто переносит уже известные origin/dest/режим/дату в FSM-состояние
мастера `/add`, пропуская повторный ввод.

**Два реальных бага, найденных живым end-to-end тестом (маршрут через хаб на реальных городах),
не ревью кода:**
1. `compose()` считал зазор пересадки между двумя `discovery`-офферами без известного времени
   (у Travelpayouts только дата, время — заглушка "полночь") как буквально 0 минут между двумя
   одинаковыми полуночами → каждая связка в тот же день ложно браковалась как "слишком короткая
   пересадка". Теперь проверка зазора/длительности запускается только если оба конца реально
   знают время; иначе — не отвергается и не подтверждается, честно неизвестно.
2. `registry` считал `EMPTY` (источник ответил нормально, просто ничего не нашёл) отказом для
   circuit breaker — маршрут с законно скудными результатами (как оказалось, ровно случай
   Яндекс.Расписаний без цен) мог словить открытие цепи после 5 пустых-но-успешных запросов.

## Адаптеры источников

Каждый источник цен — класс, реализующий протокол `SourceAdapter` (`adapters/base.py`):
`search()` никогда не бросает исключение, вся политика retry/backoff/circuit-breaker/кэша
живёт в общей обёртке реестра (`adapters/registry.py`), а не в самом адаптере. Добавление
нового источника — один новый файл + одна строка регистрации.

Два тира: `discovery` (дёшево, пакетно, может быть устаревшим) и `confirmation` (узкий live-запрос
к конкретному сайту перевозчика). Сейчас подключены `travelpayouts` (авиа-цены) и `yandex_rasp`
(жд-расписания), оба discovery. Прямые адаптеры авиакомпаний (Rossiya, S7 и т.д.) не построены —
для них нужно вручную найти реальный JSON/XHR-эндпоинт через devtools в браузере, чего
инструментами агента сделать нельзя; отложено намеренно, не забыто.

**Находки при живой проверке (не из документации — проверено запросами к реальным API):**
- Travelpayouts `v2/prices/month-matrix` не даёт ни авиакомпанию, ни номер рейса, ни точное
  время — только дату, цену, число пересадок и суммарную длительность. Поэтому
  `Leg.carrier`/`number`/`arrive_utc`/`tz` опциональны (`time_precision` показывает честно, когда
  время — просто дата), а адаптер отбрасывает рейсы с пересадками (`number_of_changes > 0`) —
  достраивать их из этих данных означало бы выдумывать хаб и перевозчика.
- У `stations_list` Яндекс.Расписаний нет поля IATA вообще, а `system=iata` работает только для
  аэропортов, не для городов/поездов — поэтому `yandex_code` для городов сопоставляется по
  названию (`seed_places.py`), не по коду.
- Для реальных поездов Москва→Питер (57 найдено на дату) — у 0 из 57 есть цена через бесплатный
  ключ. Расписания работают, цены — нет; см. README "Известное ограничение".

## Ключевые решения и почему

- **SQLite вместо сервера БД** — нулевой холостой RAM на боксе с 1GB.
- **Без headless-браузера никогда** — Playwright/Selenium съедают 300-500MB на инстанс. Если
  сайт защищён по TLS-отпечатку — обход через `curl_cffi`, не браузер.
- **Python, не Go/Node** — узкое место не CPU (I/O-bound, вежливые паузы к источникам), а скорость
  добавления нового адаптера; для реверс-инжиниринга сайтов у Python богаче экосистема и примеры.
- **Секреты vs тюнинги разделены** — `.env` только для токенов/ключей, `config.yaml` для лимитов
  (кол-во воркеров, HTTP-конкурентность, TTL кэша и т.д.) — поднять лимиты на новом VDS = поменять
  конфиг, не код.
- **Аварийная остановка только для владельца** — `/stop` проверяет `ADMIN_TG_ID`; systemd юнит на
  `Restart=on-failure`, чтобы чистая остановка не перезапускалась сама. cgroup-лимиты (`MemoryMax`)
  гарантируют, что бот не заберёт ресурсы у Tailscale/SSH на той же VDS вне зависимости от команд.
- **Заложена, но не построена generalization под ЖД-конкурентов/автобусы/другие страны** —
  `Mode` enum, поле `countries` у адаптера, таблица пересадок с fallback по стране — см. план §1/§5/§8.

## Тесты

17 тестов (`mypy --strict` + `pytest`, оба чистые):
- `tests/adapters/test_travelpayouts.py`, `tests/adapters/test_yandex_rasp.py` — каждый адаптер
  на записанном реальном/по-документации-корректном ответе (`tests/fixtures/`); при поломке
  источника цикл починки: записать новый fixture → поправить парсер → тесты зелёные.
- `tests/test_walking_skeleton.py` — интеграционный тест всей цепочки на временной SQLite.
- `tests/test_notifier.py` — тихие часы (переход через полночь), дедуп/дневной лимит уведомлений.
- `tests/test_registry.py` — регрессия на баг №2 выше (EMPTY не должен открывать circuit breaker).

Баг с составлением маршрутов через хаб (описан выше) пойман не тестом, а живым end-to-end
прогоном на реальных API — фиксирую здесь как метод: юнит-тесты на моках не увидели бы эту
проблему, поскольку баг был именно в том, *какие* данные реально отдаёт источник.

Реальный баг, пойманный раньше интеграционным тестом: `notifications_sent.sent_at` и
`users.created_at` писались через `datetime('now')` SQLite (другой формат строки, без смещения),
а читались через `datetime.fromisoformat()` — молча ломало cooldown и дневной лимит. Переписаны
на явный `datetime.now(timezone.utc).isoformat()`, как везде в проекте.

`data/seed_places.py` тестами не покрыт (дёргает живые сетевые дампы) — проверен вручную:
загрузка, идемпотентность повторного запуска, привязка аэропортов к городу, определение Москвы
как хаба, сопоставление 296/335 городов с `yandex_code` по названию.
