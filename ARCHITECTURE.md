# Архитектура

Полное обоснование решений и историю ревизий — см. [plans/squishy-scribbling-dawn.md](plans/squishy-scribbling-dawn.md).
Этот файл — сжатый снимок текущей структуры, обновляется вместе с кодом.

## Что делает проект

Telegram-бот, работающий на одном процессе (VDS 1 vCPU / 1GB RAM / 15GB disk, Ubuntu 24.04):
опрашивает источники цен на авиа- и жд-билеты по маршрутам, заданным пользователем через бота,
и уведомляет, когда цена падает ниже порога. Поддерживает разовый интерактивный поиск (`/search`)
и фоновый мониторинг (`/add`).

## Структура каталогов

```
src/aviapars/
├── config.py           # pydantic-settings: секреты из .env, тюнинги из config.yaml
├── db/                  # engine, миграции, репозитории
├── telegram/             # aiogram: bot.py, handlers/, keyboards, FSM states, format.py
├── scheduler/             # tick loop, job queue, worker pool
├── adapters/              # один модуль = один источник цен (см. "Адаптеры" ниже)
│   └── airlines/           # авиакомпании — общий базовый класс + подкласс на каждую
├── domain/                # combiner (единая точка входа поиска), validator, dealer
├── notify/                 # форматирование и рассылка уведомлений
└── health/                  # circuit breaker состояние источников

data/migrations/           # пронумерованные .sql, без ORM/Alembic
deploy/                     # systemd unit, deploy.sh, INSTALL.md
tests/fixtures/               # записанные реальные ответы источников — на них тестируются адаптеры
```

## Поток данных

Два входа в один и тот же домен:

```
/add → routes (БД) → scheduler (тик 60с) → worker → \
                                                       combiner.search_itineraries() → validator → dealer → notifier → Telegram
/search → напрямую, синхронно ──────────────────────/                                (только по пути scheduler)
```

`combiner.search_itineraries()` — единственная функция, которая отвечает на вопрос "как добраться
из A в B". И фоновый мониторинг, и `/search` вызывают её же, различаясь только `SearchOpts`
(какие тиры источников разрешены, можно ли ходить в сеть, сколько есть времени). Ветвление логики
подбора хабов/пересадок/ранжирования нигде не дублируется.

## Адаптеры источников

Каждый источник цен — класс, реализующий протокол `SourceAdapter` (`adapters/base.py`):
`search()` никогда не бросает исключение, вся политика retry/backoff/circuit-breaker/кэша
живёт в общей обёртке реестра, а не в самом адаптере. Добавление нового перевозчика —
один новый файл + одна строка регистрации, ничего в остальном коде не меняется.

Два тира: `discovery` (дёшево, пакетно, может быть кэш/устаревшим — Travelpayouts, Yandex.Расписания)
и `confirmation` (узкий live-запрос к конкретному сайту перевозчика — Rossiya, S7 и т.д.).
Причина устройства так — открытые агрегаторы (Aviasales/Yandex Travel/Tutu/Т-Банк) не дают
реальный доступ без трафика в тысячи MAU; единственные источники без такого порога — сайты
перевозчиков напрямую.

## Ключевые решения и почему

- **SQLite вместо сервера БД** — нулевой холостой RAM на боксе с 1GB.
- **Без headless-браузера никогда** — Playwright/Selenium съедают 300-500MB на инстанс. Если
  сайт защищён по TLS-отпечатку — обход через `curl_cffi`, не браузер.
- **Python, не Go/Node** — узкое место не CPU (I/O-bound, вежливые паузы к источникам), а скорость
  добавления нового адаптера; для реверс-инжиниринга сайтов у Python богаче экосистема и примеры.
- **Секреты vs тюнинги разделены** — `.env` только для токенов/ключей, `config.yaml` для лимитов
  (кол-во воркеров, HTTP-конкурентность, TTL кэша и т.д.) — поднять лимиты на новом VDS = поменять
  конфиг, не код.
- **Аварийная остановка только для владельца** — `/stop` проверяет `ADMIN_TG_ID`; systemd юнит на
  `Restart=on-failure`, чтобы чистая остановка не перезапускалась сама. cgroup-лимиты (`MemoryMax`)
  гарантируют, что бот не заберёт ресурсы у Tailscale/SSH на той же VDS вне зависимости от команд.
- **Заложена, но не построена generalization под ЖД-конкурентов/автобусы/другие страны** —
  `Mode` enum, поле `countries` у адаптера, таблица пересадок с fallback по стране — см. план §1/§5/§8.

## Тесты

Каждый адаптер тестируется на записанных реальных ответах (`tests/fixtures/`) — при поломке
сайта источника цикл починки: записать новый fixture → поправить парсер → тесты зелёные,
без тыканья в прод.
